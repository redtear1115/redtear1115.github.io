# 交稿前檢查表

**一項一項跑。** 合成一次掃會漏掉 — 這是在 slop taxonomy 上量過的。

單一條命中不代表什麼，**成群出現才要重寫**。

## 結構

1. **開場**　第一段是不是題目導覽（「在當今的前端開發領域…」／「Astro 是一個…」）？
   → 改成從你真正遇到的情況開，錯誤訊息、數字、當下的卡點。
2. **開場公式化**　是不是又一次「你有沒有過那種，⋯⋯的經驗？／我有。」？
   這個句型本身沒問題，但這個站已經用了 28 次。→ 這篇換個開法。
3. **假裝成散文的條列**　整段其實是「第一…第二…第三…」？
   → 要嘛老實用條列或表格，要嘛寫成有論點的段落。
4. **每層都在摘要**　每節開頭預告、中間講、結尾再總結一次？
   → 只在它該待的層級講一次。
5. **每節等長**　是不是每個 `##` 都剛好三到四段？
   → 依有趣程度重新分配篇幅。
6. **結尾殘留**　`## 收尾` 裡有沒有「總結來說…」、「未來展望…」、把上面講過的再講一次？
   → 內容講完就停。收尾只放結論、沒解的問題、下一步。

## 內容

7. **沒有失敗**　全篇每一步都成功？
   → 補上你先試了什麼、哪裡壞掉、下次會跳過什麼。**這是讀者最信的部分。**
8. **沒有立場**　比較了幾個做法卻不給建議？
   → 給推薦，並附上「什麼情況下我會改變主意」。
9. **自創名詞**　文章中途發明了一個詞（「設定漂移症候群」）？
   → 用白話描述，或用業界既有名詞。
10. **程式碼沒跑過**　出現 `foo`、`my_service` 這種從沒執行過的範例？
    → 換成你實際跑的那一份，或明講這是示意。
11. **數字沒條件**　貼了效能數字卻沒寫機器、版本、資料量、跑幾次？
    → 補條件，或整個拿掉。
12. **具體資訊是真的嗎**　版本號、路徑、參數名、錯誤訊息、commit sha — 全部要是實際看到的。
    **不確定就去查或留 TODO，絕對不要編。** 自信地講錯是最高等級的破綻。

## 表面

13. **AI 客服殘留**　「希望這篇對你有幫助」、「讓我們開始吧」、「很棒的問題」。→ 刪。
14. **廢話密度**　同樣的內容能不能用一半篇幅講完？
    「在這個快速變遷的時代」、「值得注意的是」資訊量為零。→ 刪。
15. **裝飾性格式**　emoji 當項目符號、粗體小標滿天飛、每個清單都剛好三點。
    → 只在真正需要強調的地方用粗體。清單長度照事實走，不要湊三。
16. **中文 AI 味**　跑 `voice-and-typography.md` 的翻譯腔表。
17. **句子節奏**　有沒有連續三句以上長度雷同（同上）。
18. **唸出來**　文法對但沒人會這樣講話的句子，用講話的語序重寫。

## 站台規則（不是 AI 味，但一樣會被退）

19. **裸 code fence**　每個 ``` 後面都有語言標記嗎？沒標會被 Shiki 當 plaintext 渲染成單色。
20. **標籤**　2–5 個，全部在 `CLAUDE.md` 的 30 個受控清單內？有沒有自己發明新的？
21. **`####`**　有沒有第四層標題？這個站不用。

## 白名單 — 這些不是 AI 味，不要改

| 不要動 | 原因 |
|---|---|
| `## 收尾` 這個固定收尾標題 | 77 篇裡 65 篇都這樣寫，是作者習慣 |
| 「我有。」這種獨立成行的短句回應 | 同上，是 Ray 的節奏 |
| 中英夾雜（pin、fallback、guard、callsite 不硬翻） | 技術文章常態，硬翻反而難讀 |
| 乾淨的文法與標點 | 很多人本來就寫得乾淨，故意寫錯字是更明顯的破綻 |
| 單獨一個破折號、單獨一個「其實」 | 一次不算，只有成群才算 |
| 真的可以列舉的東西用條列 | 表格和清單本來就是對的工具 |
| 安裝步驟那種短促、無修飾的句子 | 簡潔是技術文章的常態 |
