# 台灣技術部落格的常見手法

歸納自幾位長期有讀者的中文技術作者。**這裡借的是「手法」，不是「語氣」** ——
語氣一律以 `corpus.md`（本站 83 篇）為準。兩者衝突時，聽本站的。

來源：Huli（blog.huli.tw）、Kalan 愷開（blog.kalan.dev）、Hiraku（hiraku.dev）、
保哥 The Will Will Web（blog.miniasp.com，當反例用）。

## 選題（Hiraku）

寫下面六種，寫出來就會有人看：

1. 別人沒寫過的東西。
2. 自己原創的新做法、新技巧。
3. **別人寫錯、或很容易有誤區的內容**——糾正型的文章特別有價值。
4. 很難被 Google 到、但很實用的技巧。
5. 自己常常用到但是會忘記的東西。
6. 對自己來說很簡單、但對別人有點難度的東西。

「你越菜，你的文章在某種程度上可能寫得越好」——新手寫的教學因為作者剛學會，
反而會把坑點寫得更細。不要因為「這太基本了」就不寫。

## 標題

實際流傳的標題形狀，可以直接套：

- **當 X 變成 Y**：〈當測量變成目標：從窗戶稅到 Pull Request 數〉
- **從 X 重新認識 Y**：〈從攻擊手法開始重新認識網路〉〈從 React 中學習 JavaScript 底層運作〉
- **否定式提醒**：〈別再用 AWS Access Key 了〉〈2026 年，你可能不需要 AWS〉
- **反直覺宣告**：〈VS Code Material Theme 不是惡意軟體——安全的線該畫在哪？〉
- **不需要 X 的 Y**：〈不需要括號跟分號的 XSS〉

共同點是**標題本身就帶一個立場或一個意外**，不是主題描述。
對照組：保哥的〈如何使用 ssh-copy-id 快速設定…〉是手冊體標題，
搜尋友善但沒有敘事張力——那是工具書的路線，不是這個站的路線。

## 開場

兩種被驗證有效的開法：

- **時序案例堆疊**（Huli）：「2026 年 5 月 19 日，拿來做圖表的套件 antv 遭到攻擊，
  最新版本被植入惡意程式。」「5 月 13 日，前端圈很熱門的 TanStack 系列 repo 也遭到攻擊。」
  連續丟兩三個真實日期與事件，再問「在這個前提下，開發者該如何保護自己？」
- **個人經歷切入**（Kalan）：「我在某次工作中，曾經自己寫了小工具，用來統計我
  （以及其他團員）本季貢獻了多少 Pull Request。」再接「我當時有點生氣」這種情緒。

兩種都在三句之內把讀者放進一個具體場景，沒有一句在介紹主題。

## 設問驅動（最值得偷的一招）

Huli 整篇文章是靠**替讀者問出他心裡的問題、然後打臉**推進的。原句：

- 「那只要不用它應該就不會有問題吧？」
- 「那我們該怎麼防禦呢？」
- 「應該很安全了，對吧？」→ 下一句：「這麼想的話，你就掉以輕心了。」
- 「寫到這裡，我們該做的看起來都做了……」→ 接：「魔鬼永遠藏在細節裡。」

用法：每講完一個段落，替讀者講出他此刻的想法（通常是「那這樣就沒事了吧」），
然後在下一行推翻它。這招跟本站既有的「誤診 → 真相」骨架是同一件事的兩種寫法，
差別在 Huli 把誤判掛在**讀者**身上，本站掛在**作者自己**身上。
**本站的版本比較適合這個部落格**，因為它是第一人稱的開發日誌；
但「應該很安全了，對吧？」這種句子可以夾在自己的誤判之前，效果加倍。

Kalan 的變體是吐槽式設問：「明明只是想要理解團隊的產出而已，為什麼反而越變越糟？」

## 人稱

- 講讀者會遇到的事用**「你」**：「當你執行 `npm install express` 時」
- 講共同處境用**「我們」**：「我們該怎麼防禦呢？」——製造作者與讀者同一陣線
- 講選擇與經驗用**「我」**：「我自己是設定 3 天」「以我寫文章當下為例」

三個人稱交替使用，不要整篇只有「我」。本站目前偏重「我」，
適度加入「你」跟「我們」會更像在對話。

## 括號吐槽

括號拿來放你「其實想講但不好意思放進正文」的話，是中文技術寫作很好用的語氣閥門：

- 「（當然不是 100% 解決這問題，畢竟沒人發現的話一樣會下載到）」
- 「你們是約好要故意不一樣的嗎……」（吐槽三種工具的版本單位不一致）

本站已經有一個同族的用法：「我又覺得自己是天才了（你看出問題了吧）」。

## 遞進編號

招式型的內容用「第一招 / 第二招 / 第三招」，比「方法一 / 方法二」有節奏感。
本站的對應寫法是「第一關 / 第二關 / 第三關」跟「我學到的三件事」。

## 結尾

不要昇華，不要展望。兩種收法：

- **承認不完美 + 給一個實踐建議**（Huli）：「總之呢，我覺得把 npm 設定好是一定要的，
  或是改用 pnpm。」後面補一個更激進的方案（dev container）當開放結尾。
- **從量化轉向質性**（Kalan）：「除了數字本身，數字外那些難以量化的事情，
  或許才是我們更值得追求的事。」

本站的標準收法（`## 收尾` → 自嘲轉身句 → 斜體時間戳）已經比這兩種更有個人記號，繼續用。
可以吸收的是「總之呢」這種**把結論講得像口頭禪而不是結案報告**的態度。

## 程式碼帶入

貼 code 之前一定有一句把讀者的眼睛帶進去：「可以看到還不少：」「會在 terminal 上看到……」
貼完之後用「例如說……」接著解釋。**不要讓 code block 自己站在兩段文字中間。**

## 不要學的部分

- 保哥式的「如何 X」「Y 入門操作手冊」標題與章節——那是工具書，SEO 強但沒人會一路讀完。
- Kalan 那種句末大量省略號留白的習慣——放在開發日誌裡會顯得沒把話講完。
- Huli 的教學式全文設問——整篇都在問會很累，本站一篇用一到兩次就夠。
