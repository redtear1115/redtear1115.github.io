9 月 10 日那天，我的 git log 裡連著出現這三行：

- 移除側面鄰棟：等距下放不下，硬放就是一排大樓貼著小店
- 路燈與行道樹改放人行道，不再杵在馬路正中央
- 城市沿後牆斜線落地，消除「店蓋在停車場中間」的楔形灰地

三個錯誤，三種形狀，但有一個共同點——**它們全部都通過了驗收**。而且驗收的人沒有偷懶，清單上每一項都查了，也都答對了。

## 先講這是什麼

`cv-store` 是我在做的一款便利商店經營模擬，復刻的是那種老遊戲：你是店長，擺貨架、排收銀動線、進貨、雇工讀生，目標是把一間小店做到存款 12 萬。斜 45 度等距視角，顧客會真的走進來逛街、拿商品、排隊結帳，動線排不好他們就繞路，繞太久就氣走。

技術上是刻意的簡陋：純前端、零依賴、零建置。ES modules 加 Canvas，開一個 http server 就能跑，沒有 npm install 這一步。全部六千多行，`game.js`／`sim.js`／`data.js`／`meta.js` 完全不碰 DOM，可以用 Node 直接 import 跑無頭平衡測試——這件事後來救了我很多次。連音效跟 BGM 都是 WebAudio 合成的，沒有一個音檔。

先說清楚：**現在還玩不到**，之後會釋出。這篇不是宣傳，是我在做它的時候撞到的一個東西。

真正花掉我最多時間的，不是顧客的狀態機，也不是 BFS 尋路。是配色。

## 為什麼那三個錯誤會過：驗收問的是「有沒有出現」

這個專案我開了好幾個 session 分工：實作、素材、驗收、美術總監，各自有各自的職責範圍。聽起來很專業對吧？我當時也這麼覺得。

然後「一排大樓貼著便利商店」就這樣過了。

去追根因的時候我發現，問題不在任何一個人身上，在**驗收委託的問法**。委託寫的是「確認左右鄰棟有出現」，驗收者去看了，鄰棟確實有出現，打勾，通過。沒有人問「這樣對不對」——而那才是這題唯一重要的問題，因為等距視角下相鄰格在螢幕上只差 32×16px，素材卻常常是 64×118px 那種尺寸，一棟樓放下去就吃掉隔壁三格。

更關鍵的是，這個專案裡唯一有構圖判斷力的角色是美術總監，而他從頭到尾**沒有看過組合後的畫面**——他只看自己的 demo 頁。

所以我補了一套三道關卡：實作者進場前先算螢幕矩形重疊（不准用肉眼）、驗收委託一律附一段開放式提問「退一步看整張圖，有沒有哪裡看起來假的、比例怪、違反物理常識」，並且明講**發現清單沒問到的錯誤是加分不是越權**，最後視覺批次收線一定要把真實遊戲截圖送給美術總監看。

寫完我又覺得自己是天才了。

## 誤診：我以為補一條規則就夠了

流程補完，我回頭去看我給 agent 的「Agent contract」，裡面早就有一條視覺層級的硬規則，寫的是「玩家的店必須是全畫面飽和度最高的東西，周邊環境只能襯托不能搶戲」，後面附一張階梯：遠景灰高樓 9~11%、臨街店鋪與左右鄰棟 18~24%、店內設備 51~100%。

這條規則有數字、有層級、也確實被遵守了。素材一張一張拿出來看，每張都合規。

問題是把它們組起來之後，店裡看起來很奇怪——貨架、冰櫃、關東煮台全都彩度爆表，而**架上有沒有貨看起來沒什麼差別**。缺貨的架子跟塞滿的架子，第一眼讀起來一樣熱鬧。

對一款「缺貨會扣人氣」的經營遊戲來說，這是致命的。整個遊戲要玩家做的事就是看畫面、判斷哪裡缺貨、然後決定補什麼——我卻把畫面做成了讀不出缺貨的樣子。

## 真相：那條階梯自己在說謊

我盯著那張表看了很久才看懂：**一條階梯在回答兩個不同的問題。**

「店在畫面上的哪裡」是明度的工作。「玩家的眼睛該被什麼抓走」是飽和度的工作。把兩個混成一條，任何人——人或 agent——照著推導，都會得出「店內設備要很彩」這個結論，因為在那條階梯上「店內」就是最上層。

但設備是**容器**，是裝東西的殼。真正該搶戲的是架上的商品和店裡的人。容器一旦跟內容物一樣彩，內容物就消失了。

所以我把它拆成兩條。明度階梯回答「店在哪裡」，從遠景建築 0.45 一路爬到店內地板 0.79~0.95——店內地板永遠是全畫面明度最高的區域，白天把天色抬亮之後仍然要低於地板。飽和度階梯則回答「該看哪裡」，設備本體被壓到 6~16%、比天空還低，街道生活道具 30~45%，顧客與店員 40~70%，架上商品 65~95%，只有品牌識別帶可以到 85~100%。

換句話說，我把設備從「第一名」直接調成「倒數第二名」，僅次於地板。這聽起來很反直覺，但一改完，缺貨的架子立刻自己跳出來了——因為架子本身幾乎是灰的，上面有沒有那幾顆高彩度的商品，差別一眼就看得出來。

那條舊規則我沒有刪掉。我把它留在 contract 裡，前面加一句「**那是錯的，不要改回去**」，後面寫清楚錯在哪。刪掉的話，下一個 session（或三個月後的我）會用同樣的直覺再推導一次，而那個直覺本身就是錯的來源。

## 自製的 demo 只會重現作者的假設

這件事還有一個尾巴，是美術總監在檢討的時候講的一句話，我直接抄進 contract 了：

「demo 是我按照自己的假設擺的，所以它只會重現我的假設，不會挑戰它。我在 demo 裡把鄰棟擺得好好的，因為擺的人是我。」

這句話對所有人成立，包括我自己。我寫的 headless 探測、驗收者自建的測試存檔、素材端的 demo 頁——這些全部只能證明「在我預期的用法下沒問題」，一個都不能證明它對。能挑戰假設的只有真實的遊戲畫面，加上別人的眼睛。

所以現在 contract 裡多了一條：任何「整排／整欄／一律」的擺法，動手前先問一句「那看起來會是什麼」。

## 收尾

我從這個專案帶走的那句話是：**規則沒有數字就會被各自解讀，但有數字的規則也可能在問錯的問題。**

前半段我早就知道——`wallHeight: 34` 寫成常數就是這個道理。後半段是這次才學到的：一條有數字、被確實遵守、每個檢查點都通過的規則，還是可以把整個畫面帶到錯的地方去，而且過程中不會有任何人報錯。它不是壞在某一行，是壞在它問錯了問題，而問題本身不會觸發任何檢查。

遊戲本體現在跑得還不錯：44 個 commit，顧客會排隊、鮮食會過期報廢、颱風天泡麵會被搶購、破產跟破關都會結束這一輪然後帶著聲望重開。釋出之前還有一輪平衡要調。

先不說了，我得去把那張飽和度表拿去對三張參考遊戲的截圖再實測一次——我有預感「顧客 40~70%」這一格還是訂得太保守了。
