9 月 18 日晚上，AI agent 在驗收別的功能時發現一件事：我自己 Mac 上真正在用的那份 [MarsDawn](https://marsdawn.southern-light.dev)，設定資料夾裡躺著 235 個不屬於它的檔案，全是跑測試剩下的，每跑一輪大約再多 15 個。連我真正的設定檔，也被測試改寫過。agent 把發現整理成一份回報，第一句就點出原因：單元測試一直頂著正式 app 的身分在跑。

這是 MarsDawn 開發的第二天。[第一天](https://southern-light.dev/blog/marsdawn-one-day-security-holes/)我把它從零做到能送審，這天主要在做側邊欄，晚上還要發 1.0.1 版。寫程式、跑測試、驗收都有 AI agent 分頭在做，我負責拍板。

每個 Mac app 都有一個獨一無二的身分標籤（bundle id），系統靠它決定這個 app 的設定存在哪、資料放在哪。單元測試是程式用來檢查自己的小測驗，MarsDawn 的這些小測驗借的就是正式 app 的身分，於是跟我真正在用的 app 共用同一個設定資料夾。測試建出來的暫存設定就堆在裡面；用一種比較省事的方式跑測試時，連資料夾外面那份真正的設定檔都會被寫到。

二十多分鐘後，同一份回報底下多了一段補充：驗收又找到另一條寫入路徑，負責統籌的 agent 追下去，發現源頭就是它自己。它一直用那種省事的方式跑整套測試，當晚就寫過一次我真正的設定檔。對照起來更尷尬的是，驗收的 agent 本來就有個習慣，操作 app 之前先複製一份、換個身分再動手，就是為了不碰到正式那份；統籌 agent 平常跑測試的方式，卻沒有這層保護。

那份回報裡寫了，agent 沒有刪我 app 資料夾裡的任何東西，建議我自己看過資料夾再刪。後來是我下了指令，agent 才把那 244 個測試和驗收留下的檔案，加上另一組測試留下的 66 個，只挑檔名完全對得上的刪掉。它也提醒我：只要測試還借用正式 app 的身分，檔案就會繼續長出來。

最直覺的修法，是讓每顆測試跑完自己把設定清掉，一開始的建議裡也有這一條。實際查下去才發現清不掉。macOS 有個管設定檔的背景程式 `cfprefsd`，測試刪掉一份設定，它過幾秒又自己寫回去，所以側邊欄那批測試的清理從來沒有真正生效過。

後來換了方向，讓測試有自己的身分，跟正式 app 分家。測試用的設定只放在記憶體裡，不寫進硬碟；測試如果掛著正式 app 的身分，就根本建不起來；另外寫了一支檢查程式包住整個測試流程，每跑完一輪就去比對正式 app 的設定，只要多一個、少一個或改了一個檔案，整輪就算失敗。這包修改當晚就併進了正式程式碼。

發 1.0.1 之前，還有一個相似的小洞。.txt 檔在 MarsDawn 裡是用唯讀方式打開的，畫面上寫著唯讀，選單裡的「儲存」卻還按得下去，按下去真的會覆寫原檔：原本用 UTF-16 存的檔案，存回去變成 UTF-8（兩種不同的文字存法）。使用者什麼都沒改，檔案的存法就被換掉了。修法同樣從根上擋：唯讀文件的儲存和另存全部停用，不管哪條路要寫回原檔都拒絕，只留下「複製一份」照常能用。這個修正和另一個行號顯示的修正，一起寫進了當晚 1.0.1 的更新說明。

這件事之後，我會問自己：拿來練習、測試的東西，跟真正在用的東西，是不是其實住在同一個地方？測試借了正式 app 的身分，垃圾就直接堆進真的設定裡。清不乾淨的時候，我是繼續加強清理，還是先問它為什麼會掉進來？連清理本身，都被背景程式在幾秒後寫了回去。

我也會問，agent 在某個場合已經養成的好習慣，有沒有被帶進每天例行的流程？驗收的 agent 動手前會先換身分，統籌的 agent 跑測試時卻沒有。要動到我真正在用的東西時，我是看過再點頭，還是直接說好？這次 agent 停下來等我下指令，才去刪那三百多個檔案。

新的檢查程式當晚就派上用場。另一組主題設定的測試原本會在硬碟上建設定，檢查程式不再放行，十一點多改成只用記憶體裡的版本。

先不說了啦，我得去確認 `cfprefsd` 今天有沒有又在背後幹了什麼好事。
