你有沒有翻過一份自己半個月前寫的設計文件，讀到一半發現——它寫的東西跟現在的 code 完全對不上,而且不是哪裡寫錯一個字,是整個結構性地錯位?那種感覺很微妙:文件還在、排版還很整齊、wiki-link 還點得進去，但它講的是一個**已經不存在的世界**。

我這兩天就在跟一整坨這種「排版整齊的謊言」奮戰。

## 罪魁禍首:我用「slice」當組織軸

先講當初怎麼種下這個雷。我這遊戲的設計文件（spec）一開始是按「開發批次」組織的——我把它叫 slice。slice1 是第一批做的機制、slice2 是第二批、slice4 是第四批。當下超合理啊:我就是一批一批做的，文件跟著開發節奏走，寫的時候完全順手。

問題出在後來。遊戲關卡順序**輪換**了一次——為了對齊初代道館順序，我把 stage 5/6/7 重排成「毒→超能力→火」。code 改了、關卡資料改了、玩起來也對了。

但 slice2 那份文件還寫著「stage5 超能力、stage6 火」。

它沒錯——在它被寫下來的那個版本，stage5 確實是超能力。只是世界變了，它沒跟著變。於是任何人（包括三天後的我自己）打開 slice2，都會讀到一份**言之鑿鑿、但已經過時**的對照表。更陰的是城市名,我同時有「山吹」跟「金黃」兩種叫法散在各檔——同一個地方兩個名字,你根本不知道該信哪個。

文件在騙人。而且是用「正式的索引 + 有效的 wiki-link」這種看起來很可信的形式騙人。

## 為什麼這種謊特別難抓

runtime 的 bug 至少還會噴錯、會掉幀、玩家會罵。文件的謊**什麼訊號都不會給你**。tsc 不會紅、測試不會掛、CI 全綠。它就靜靜躺在 repo 裡，等一個倒楣的人——通常是未來的你——照著它去做事，然後做出一個對不上現況的東西，再花半天 debug 才發現「啊原來是文件就錯了」。

我盯著這堆 slice 檔想了一下，意識到根因不是「我忘了更新文件」。根因是我**選錯了組織軸**。

「slice」是一個**短命的東西**。它描述的是「我第幾批做這件事」，這個資訊一旦做完就失去意義了——沒有人在玩遊戲的時候會 care 某個機制是第二批還是第四批做的。我把文件掛在一個註定會過期的軸上,它當然會腐爛。

## 修法:換成永久的軸

所以這次重構的核心不是「逐字訂正」，是**換軸**:把組織軸從 slice（開發批次）改成 stage（關卡）。

stage 是**永久的**。只要遊戲還有第五關,「stage5 是什麼屬性、有哪些雜兵、什麼機制」這個問題就一直有意義、一直對得上 code。我把 slice1/2/4 的內容拆開,按它們實際影響哪一關,塞進各關的 curriculum spec 裡（睡眠混亂→stage6、毒→stage5、道中精英→stage8…），然後**把 4 個 slice 檔直接刪掉**。

刪檔這步我猶豫了一下,畢竟那是有寫過的東西。但留著一份過時的文件,比沒有文件更糟——沒有文件你會去看 code,過時的文件你會相信它。順手把所有斷掉的 wiki-link 回連修好、城市名統一成「金黃」、9 關 curriculum 的格式對齊,驗證 0 斷連。

## 教訓:組織軸要選會留下來的東西

這件事我學到的一條,可以遷移到任何專案的文件:

**文件的組織軸,要挑「產品上永久存在的東西」,不要挑「當下開發方便的東西」。** 按 sprint、按 PR、按「第幾批」、按「哪個工程師做的」來組織文件,寫的當下都很順,但這些軸全都會過期。一旦過期,文件不會消失,它會變成考古層——排版完好、內容說謊。

挑會留下來的軸:功能模組、產品實體（我的例子是 stage)、使用者旅程。這些東西只要產品還活著就一直在,掛在上面的文件才有機會跟著 code 一起老,而不是各老各的。

某種程度上這跟我前幾天修的那些 runtime bug 是同一個病——「看起來合法、其實在騙人」,只是這次的舞台從遊戲引擎換到了 docs 資料夾啊。

先不說了,我得去把 README 裡那個 slice archive 區也清掉,免得哪天又有人(我)點進去信了它。
