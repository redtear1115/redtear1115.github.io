你有沒有過那種，同一個 bug 換了張臉出現三次，你每次都當成新案子在修，修完才發現根子其實是同一句你一直沒問過的話？我這兩天就撞了三次，一次是 balance、一次是幣別鎖、一次是我自己坐下來把規則寫進 CLAUDE.md 才真的想清楚。

## 第一次：新伴侶繼承了舊關係的爛帳

Futari 的 `recalcGroupBalance` 邏輯很單純——把這個 group 底下所有沒被 soft-delete 的 transaction 全部加總一遍。這個設計我自己也寫過文章吹過（見另一篇 balance 重構），當時覺得「every write 都全表重算」已經夠無腦、夠安全了。

我漏掉的是：group 的 `member_b` 是會換的。一個人退出關係、新的人加入，epoch 開了新章節，但 `recalcGroupBalance` 完全不知道「章節」這回事——它只認 group id，不認你現在在哪一段關係裡。結果新伴侶一進來，balance 直接繼承了上一段關係留下的殘值，兩個人的帳本第一天就是錯的。

修法看起來很直覺：balance 公式加上 epoch 範圍，只算當前章節內的 transaction。收工，我以為。

## 第二次：同一根柱子，換了個角度撞上

補這個修正的當下順手做了個安全檢查，才發現我用來判定「這筆交易屬於哪個 epoch」的欄位是 `transacted_at`——也就是使用者填的交易日期。

問題來了：如果使用者是在新章節開始後，去**補記**一筆發生在舊章節時間點的歷史收據呢？`transacted_at` 會落在 epoch 邊界之前，這筆帳就會被算法直接甩出當前 epoch，balance 靜默漏算一筆——不會報錯，只會讓數字對不上，而且對不上的方向沒有規律，很難用肉眼抓。

改成用 `created_at`（這筆 row 實際寫進 DB 的時間）判定歸屬，問題才真的消失。

## 第三次：我以為兩次就夠了

隔天處理幣別鎖（`base_currency` 只能在當前 epoch 無 record 時修改），一開始很自然沿用舊習慣，拿 `transacted_at` 當判準。寫到一半整個人愣住——欸，這不就是昨天那個坑嗎？只是換了個欄位而已。

我這才意識到，我修了兩次的其實是同一個問題：**「這筆資料屬於哪個時間切片」這個問題，答案永遠該是「它被系統認定存在的那一刻」，不是「使用者說它發生的那一刻」。**這兩個時間戳平常長得幾乎一樣，只有補登、跨時區、章節交界這幾種邊界情境會讓它們分道揚鑣，而系統設計如果沒有明確表態要用哪一個，每個新功能都會各自賭一次，賭錯的機率是均分的。

所以幣別鎖直接收斂成單一來源，一律用 `created_at`。做完這件事我才回頭去補了那份最無聊但最重要的文件：在 CLAUDE.md 裡把「`transacted_at` 是使用者說的時間，`created_at` 是系統寫入的時間，任何跟 epoch 歸屬有關的判定一律用後者」白紙黑字寫下來。

## 教訓拉高一層

說起來有點糗——三次踩雷用的是完全不同的功能（balance、幣別鎖、之後大概還會有別的），但拆開看底層根本是同一個問題，我一直沒回答過。如果第一個 epoch 相關功能寫的時候，我就先問一句「這個時間戳，我要的是使用者說的，還是系統認定的」，後面兩次根本不用發生。

可遷移的教訓是：**任何欄位一旦跟「這筆資料屬於哪個時間切片」扯上關係，第一次遇到就該把答案寫進文件，不要只改 code。**改 code 只解決眼前這個 call site，寫文件才會讓下一個功能在動筆之前就先問對問題。

先不說了，我得去把 repo 裡還有沒有別的地方偷偷用 `transacted_at` 判 epoch 也抓一遍——我現在看到這個欄位名字會反射性緊張。
