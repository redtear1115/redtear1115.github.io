Futari 是給兩個人一起記生活帳的家計簿。兩個人分開之後，留下來的人可以再邀請別人，同一本帳就開了新的一章，舊章節留著，只是不再算進現在。

9 月 12 日傍晚六點半，一張票開出來。算欠款的公式從來不看章節。A 付了一千元兩人對半，B 還了五百，B 離開，C 加入，兩個人記下第一筆帳，C 就憑空欠了 A 五百。查過正式環境，九個雙人帳本都還沒有關閉過的章節，沒有人真的踩到，修的是下一個會踩到的人。

修法聽起來很簡單，欠款只算這一章。那一筆帳算哪一章，要看一個日期，而帳上有兩個日期：這筆錢發生的那天，還有這筆帳被記進系統的那一刻。平常這兩個日期幾乎一樣，今天吃飯今天記。

agent 去查專案裡寫給它看的那份說明書，上面寫得很明白：帳要看「發生日」落在哪一章。這句話五月就在裡面了。它照著寫，測試也寫了，修之前紅、修之後綠，全套測試通過，晚上八點半開了 PR。

另一個 agent 驗證完，判定不通過。

它試了一個很日常的情境：新章節第一天，補記一張昨天的收據。發生日在上一章，所以欠款不算它。更糟的是匯入。Futari 有一頁在教大家把舊帳從別的 App 搬過來，一整本歷史的發生日全在章節開始之前，匯完之後欠款是零。那些紀錄在列表上看得到，欠款卻一筆都沒算，也沒有任何錯誤訊息。

翻開程式碼，列表、統計這些地方判斷章節，十六處全部用「記下的時間」。只有說明書寫的是另一個，這個 agent 認真照著做，就踩進去了。

八點四十二分，第二版改用記下的時間。前一版的測試還是綠的，新伴侶憑空欠錢這件事照樣擋得住。九點零三分合併。

合併之前，八點五十六分又開了一張票，專門改那一句話。我喜歡這張票的地方，是它沒有只叫人把字改掉，它說這題要回答哪一個才是對的，而且這是產品判斷，應該寫下來。章節是一段關係的分期，昨天的收據今天補，它還是在這段關係裡被記下的，所以看記下的時間。可是「那個月花了多少」就要看發生日，月度回顧本來就用得對。

後來寫進去的是一張分工表：哪個問題用哪個日期，還有用錯的時候長什麼樣子。列表有、欠款沒有、沒有錯誤訊息。晚上十點五十四分合併。

我以為這事到這裡結束了。

隔天中午，新的票來了，裡面貼的就是前一晚才寫進去的那段話。Futari 的設定頁有一道鎖：這一章已經有紀錄，就不能改主要幣別。這道鎖用的是發生日。匯入一批去年的帳，它數出來是零筆，放行。Futari 的金額存成數字，改幣別不會換算，一千元台幣就安靜地變成一千日圓，整本帳對得起來，看不出哪裡不對。

這道鎖還有兩份，設定動作一份，設定頁一份，各數各的。有一個舊測試更妙，它測「章節之外的紀錄不擋」，用的就是發生日，等於把這個錯寫成了規格。當天晚上七點二十五分，兩份收成一份，只回答一個問題：這一章有沒有紀錄。七點三十七分合併。

這份說明書前一天才害我們一次，隔天那張票就拿它當根據，指出另一個藏得更深的。差別只在那一句話對不對。

這件事之後，我對寫給 agent 的文件比較緊張。人讀到一句奇怪的話，可能會嘀咕一下、去問別人。agent 會照做，還會補上測試，把那句話變成綠燈。這次擋下來，是因為另一個 agent 沒有拿那份文件當答案，它自己去試了補記收據。

Futari 的程式碼在 [GitHub](https://github.com/redtear1115/oikos)，iPhone 和網頁版都在[作品集](https://southern-light.dev/works/)裡。

先不說了，我得去把寫給 agent 的那份說明書，再從頭讀一遍。
