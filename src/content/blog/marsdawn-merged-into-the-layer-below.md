[MarsDawn](https://marsdawn.southern-light.dev) 是我做的 Mac 版 Markdown 編輯器，左邊寫、右邊看預覽，iPhone 和 iPad 上也有一個看文件用的版本。Mac 的下一版 1.2.2 要帶一組「列印與匯出」的改動：存檔時不冒險蓋掉舊檔，PDF 可以加封面，收折起來的段落匯出時可以選要不要展開。

這三件事是同一個 agent 接著做的，後一件要用到前一件的程式，所以三張 PR 一張疊一張。最底下那張的合併目標是主線，第二張的目標是第一張的分支，第三張的目標是第二張的分支。這樣每一張打開來，只看得到它自己那一層的改動，審的人比較好讀。

11 月 8 日我決定替這一版另開一條發版分支，要出貨的東西都收到那裡。當時我附了一個條件：PR 改目標的時候，疊起來的順序要留著。

疊著有一個代價。自動測試只在目標是主線或發版分支的 PR 上跑，目標指著別張 PR 的那兩層，推了新的修改也沒有人測。11 月 9 日我給了一個通用的同意：要跑測試時，把目標暫時改成發版分支，跑完改回來。

最上面那張收折的 PR，從 9 日深夜到 10 日早上這樣來回了三次。每一次 agent 都在 PR 上留一句，寫明是為了哪一次修改、測試的連結在哪，結尾是「跑完會改回」。三次都改回去了。10 日早上八點四十一分，驗證的 agent 寫下通過。八點四十八分，MacBook Air 上的測試員回報：沒有封面的時候，「封面圖片」選單上方的標籤有跟著變灰，淺色深色都看過。

下午五點零一分，我開始合併。由下往上，第一張、第二張、第三張，前後 38 秒，三張都變成紫色的「已合併」。

第一張進了主線。第二張的目標是第一張的分支，它就合進那條分支，而那條分支十七秒前已經合完了，沒有人會再把它往前送。第三張一樣，合進了第二張的分支。下層合併之後，上層的目標沒有自動改指到別的地方，這個 repo 合併完也不刪分支，三張各自停在當初指的那一層。

所以封面和收折，主線沒有，發版分支也沒有。第一張也只到主線。這一版要出貨的那條發版分支，三張一張都沒拿到。

早上那三次「改回去」，每一次都照說好的做了。也因為每一次都照做，我按下合併的時候，上面兩張的目標都還指著自己的下一層。

晚上七點五十三分，輪到 iPhone 版的那一疊，一共七張。這次最上面那張先合進它的下一層；七點五十四分，第二高那張的目標改成發版分支；接著底下五張由下往上合，最後才合它。整疊的內容都在它身上，七點五十六分，iPhone 版的東西全數到了發版分支。

負責驗證的 agent 那時正在替這一疊整理測試單，它的工作日記先記了一筆：派工後六張就被合併了，最底下那張進了主線。專案經理 agent 隨後更正，整疊已經進了發版分支。

晚上九點五十六分，做列印面板的 agent 開了一張新的 PR，開頭寫：這張是補救用的，程式一行都沒改，只換了合併目標。底下把下午的經過列成三行，哪一張進了哪裡。這張 PR 從第二張的分支開出來，三張的內容都在上面，對發版分支是 22 個檔案。

三十三秒後它又留了一句：這張的自動測試它先取消了，因為測試員正在 MacBook Air 上跑 iPhone 版的測試，自動測試用的也是那一台，等測試員跑完再重跑。

九點五十七分我按了合併，離它開出來 72 秒，這張 PR 自己的測試一次都沒有跑完。合進去之後，發版分支自己觸發的那一輪在十點十一分綠了。

下午那 38 秒裡，我看的是三個紫色的「已合併」。合併到哪裡，寫在每張 PR 標題底下的那一行小字，我沒有看。

MarsDawn 在[作品集](https://southern-light.dev/works/)裡。

先不說了，我得去看看還疊著的那幾張 PR，目標各自指著哪裡。
